# 通用 CLI 开发规范

## 1. 适用范围

本文用于指导可独立安装和执行的命令行程序设计、开发、测试与发布，适用于使用 Node.js、Go、Rust、Python 等技术实现的 CLI。

本文只约束 CLI 产品本身，不定义 Plugin、Agent、Skill、MCP、IDE 扩展或具体业务项目的目录和发布方式。上层集成可以调用 CLI，但不能绕过 CLI 已定义的安全、校验和输出契约。

文中的“必须”“不得”是发布门要求；“应该”“建议”是默认工程选择，偏离时应记录原因。

## 2. 产品目标

一个可维护的 CLI 应同时服务两类调用者：

- 人类用户：提供清晰的帮助、交互提示、预览、确认、进度和恢复建议。
- 自动化调用者：提供完整的非交互参数、稳定 JSON、稳定退出码和可预测的副作用。

交互模式和命令模式必须复用同一业务服务，不能各自实现一套规则。向导是命令能力的易用入口，不是唯一入口。

## 3. 命令模型

### 3.1 命名

命令应该遵循“名词 + 动词”或“动作 + 明确参数”的稳定结构：

```text
tool resource add
tool resource list
tool resource show --name demo
tool run --resource demo --target sample
```

- 命令、选项和枚举值使用小写英文及连字符。
- 同一概念只能有一个正式名称；兼容旧名称时通过显式别名处理。
- 不使用 `do`、`process`、`handle` 等无法表达结果的空泛动词。
- 删除、覆盖、发布、迁移等高影响动作必须在命令名或选项中可见。

### 3.2 参数

- 必需参数必须由解析器声明为必需，不能等到执行中途才发现缺失。
- 布尔选项默认关闭；会降低安全性的选项不得默认开启。
- 多值参数必须说明分隔符、是否允许重复、去重规则和有效值。
- 时间、大小、端口、并发数等数值必须限定范围并说明单位。
- 路径参数必须解析为绝对路径后再进行边界校验。
- 不得用空字符串、特殊魔法值或参数组合隐式表达另一种模式。

### 3.3 兼容性

- 已发布的命令名、选项名、JSON 字段、错误码和退出码属于公共契约。
- 新增可选字段通常可以向后兼容；删除、改名或改变语义必须按破坏性变更处理。
- 废弃项应先发出明确警告，提供替代方式和移除版本。

## 4. 交互与非交互模式

### 4.1 TTY 判断

- 只有 stdin 和 stdout 均为 TTY 时才允许启动交互问答。
- 管道、CI、重定向或 `--json` 模式不得等待人工输入。
- 非交互输入不足时必须快速失败，返回稳定错误码和缺失字段清单。

### 4.2 交互流程

交互流程应该遵循以下顺序：

1. 收集必要输入。
2. 校验格式和业务约束。
3. 展示目标、范围、输出位置及风险。
4. 对写入、安装、覆盖或安全降级请求明确确认。
5. 执行操作并显示阶段进度。
6. 输出完成结果或可执行的恢复建议。

不得先执行不可逆操作，再询问用户是否同意。默认答案应选择风险更低的行为。

### 4.3 自动化模式

- 自动化模式必须能够通过参数、配置和环境变量完整表达操作。
- `--yes` 只代表批准当前命令已声明的副作用，不得跳过参数校验、安全校验或权限检查。
- 自动安装、删除、覆盖和发布必须分别提供显式选项，不能由 `--yes` 暗中启用。

## 5. 帮助与文档

### 5.1 `--help`

根命令帮助必须包含：

- 一句话说明产品做什么和不做什么。
- 全局选项及其影响。
- 可用子命令。
- 最短可运行示例。
- 查看子命令帮助的方法。

关键子命令帮助必须包含：

- 前置条件。
- 参数含义、默认值和有效范围。
- 至少一个使用模拟信息的完整示例。
- 输出位置或可观察结果。
- 安全风险或副作用。
- 交互与非交互行为差异。

帮助示例必须可复制，且与当前解析器契约一致。不得在示例中使用真实主机、账号、Token 或密码。

### 5.2 README

README 应按新手完成任务的顺序组织：

1. 产品边界。
2. 运行环境。
3. 60 秒快速开始。
4. 模拟输入及预期结果。
5. 常用命令。
6. 配置与秘密。
7. 常见错误与恢复。
8. 开发和发布入口。

README、`--help` 和实际行为必须同步更新，并通过自动化测试锁定关键帮助文本。

## 6. 输出契约

### 6.1 stdout 与 stderr

- stdout 只承载命令的主要结果。
- stderr 承载进度、警告、诊断和错误。
- 二进制内容不得与文本日志混用同一输出流。
- 使用管道时，颜色、动画和光标控制默认关闭。

### 6.2 JSON 模式

建议提供全局 `--json`。成功输出应包含：

```json
{
  "ok": true,
  "command": "resource list",
  "items": []
}
```

失败输出应包含：

```json
{
  "ok": false,
  "command": "resource list",
  "error": {
    "code": "CONFIG_INVALID",
    "message": "配置内容无效。",
    "details": {}
  }
}
```

- 每次命令只能向 stdout 输出一个完整 JSON 文档。
- JSON 字段必须使用稳定名称和类型。
- 不得把堆栈、进度动画、ANSI 转义或秘密混入 JSON。
- `message` 面向人类，自动化分支必须依据 `code`，不能解析自然语言。

## 7. 错误与退出码

CLI 必须定义有限、稳定的错误类别。推荐退出码分层：

| 退出码 | 类别 | 示例 |
|---:|---|---|
| 0 | 成功 | 操作完成且结果通过回验 |
| 1 | 运行失败 | 远端拒绝、导出失败、未知运行异常 |
| 2 | 调用错误或需确认 | 参数无效、缺少确认、非 TTY 调用交互命令 |
| 3 | 配置或凭证错误 | 配置损坏、凭证缺失、版本不支持 |
| 4 | 本地依赖错误 | 缺少外部工具、运行时版本不足 |
| 5 | 文件系统或状态冲突 | 目标锁定、路径不安全、并发写入冲突 |

错误对象应该保留原始原因，但默认用户输出不得展示秘密、完整环境变量或无关堆栈。调试模式也必须先脱敏。

## 8. 配置与秘密

- 配置文件只保存非秘密信息和秘密引用。
- 密码、Token、私钥和含凭证 URL 不得进入普通配置、命令参数、日志、错误详情、遥测或生成物。
- 交互输入秘密时必须关闭回显。
- 自动化场景通过进程环境、操作系统凭证库或 CI Secret 注入秘密。
- 凭证文件必须使用当前用户最小权限创建，并在读取前验证权限和文件类型。
- 删除配置时，只能在确认秘密引用未被其他配置使用后删除对应秘密。
- 示例统一使用 `<REDACTED>`、保留域名或明显的占位符。

## 9. 文件系统安全

- 所有输出必须限制在用户明确选择或产品声明的根目录内。
- 路径拼接前验证用户片段，拒绝绝对路径、父目录跳转、空片段和平台保留名称。
- 写入前检查目标链路中的符号链接、junction 和重解析点。
- 不得对工作区根目录、用户主目录或未解析变量执行递归删除。
- 临时目录使用随机且不可预测的名称，并在成功或失败后清理。
- 覆盖已有内容前先建立可恢复状态；重要数据优先使用备份或原子替换。

### 9.1 文件事务

跨多个文件的操作应使用事务式流程：

```text
准备暂存目录 → 生成全部内容 → 校验暂存结果 → 获取锁 → 原子替换 → 回验 → 清理
```

任一步失败时，旧结果必须保持可用。异常终止后，下一次运行应能根据持久化日志恢复或安全停止。

## 10. 外部进程与依赖

- 使用参数数组调用子进程，不拼接未经验证的 shell 字符串。
- 为外部进程设置超时、工作目录、环境变量白名单和秘密脱敏规则。
- 同时捕获 stdout、stderr、退出码和是否超时。
- 针对不同平台或不同实现的同名工具，显式处理参数能力差异。
- 自动安装前必须展示工具、官方来源、命令、权限、下载影响和可回滚方式。
- 默认只诊断依赖，不自动安装；安装必须由单独选项和明确确认开启。

## 11. 并发与幂等性

- 对同一逻辑目标的写入必须加锁。
- 锁记录应包含进程、主机、创建时间和目标标识。
- 只有能证明持有者已失效时才能回收陈旧锁。
- 重试不得造成重复记录、重复发布或部分覆盖。
- 已成功完成的步骤应支持幂等回验，不能仅依赖“命令没有报错”。

## 12. 架构边界

推荐将 CLI 拆分为以下层次：

```text
参数解析 / 交互适配
        ↓
应用服务与业务规则
        ↓
配置、文件事务、外部工具、远端适配器
```

- 参数解析层只负责输入映射、确认和输出格式。
- 应用服务不读取终端、不打印日志，也不依赖具体命令库。
- 外部适配器统一处理进程、网络、编码和平台差异。
- 领域类型和稳定错误码应位于共享层。
- 交互与非交互入口必须调用相同应用服务。

## 13. 测试规范

最低测试层级：

1. 纯函数测试：参数规范化、路径、配置 schema、错误映射。
2. 服务测试：业务规则、幂等性、事务提交与回滚。
3. CLI 契约测试：帮助文本、退出码、stdout/stderr、JSON 结构。
4. 打包测试：从生成的安装包启动，而不是只运行源码。
5. 平台测试：Windows、macOS、Linux 的路径、编码和外部工具差异。
6. 真实集成测试：在脱敏测试环境验证远端服务和官方客户端。

每个缺陷修复都应先建立能捕获原始症状的快速回归测试。测试不得依赖开发者主目录、真实凭证或未声明的本机工具。

## 14. 发布规范

发布前至少完成：

- 静态检查、单元测试和构建。
- `--help` 与 README 示例校验。
- 生产依赖安全审计。
- 安装包文件清单检查，排除源码秘密、测试夹具和临时文件。
- 从空目录安装候选包并执行 `--version`、`--help` 和核心只读命令。
- 对支持的平台和外部服务完成分层验收并保存证据。
- 确认版本、标签、制品和发布来源一致。

发布后必须从公共 registry 或正式分发源重新安装验证，不能用本地缓存或源码构建代替。

## 15. 可观察性与隐私

- 日志应包含命令阶段、目标的非秘密标识、耗时和稳定错误码。
- 默认不采集遥测；启用遥测必须明确告知、最小化数据并允许关闭。
- 不记录命令完整环境、认证头、连接 URL、密码或用户文件内容。
- 诊断包生成前必须脱敏，并向用户展示将包含哪些文件和字段。

## 16. 完成定义

一项 CLI 变更只有满足以下条件才算完成：

- 人类用户能从 `--help` 和 README 独立完成操作。
- 自动化调用者能在无 TTY 环境稳定执行或获得明确失败。
- 成功结果经过回验，而不是仅依据退出码推断。
- 失败不会留下半完成状态、明文秘密或无法恢复的文件。
- 新增命令、选项、JSON 字段和错误码均有契约测试。
- 构建产物和正式安装包包含所需文件且不包含不应发布的内容。
- 本地测试、跨平台测试、真实集成和公共发布验证被分别记录，不互相替代。

## 17. 评审清单

提交 CLI 变更前逐项确认：

- [ ] 命令名称能直接表达用户结果。
- [ ] 交互流程有等价的非交互能力。
- [ ] 非 TTY 和 `--json` 不会等待输入。
- [ ] stdout、stderr、JSON 和退出码符合契约。
- [ ] 示例使用模拟信息且可复制。
- [ ] 密码、Token 和含密 URL 不进入参数与日志。
- [ ] 写入路径已做边界与符号链接检查。
- [ ] 多文件写入具备事务、锁和失败恢复。
- [ ] 外部进程有超时、脱敏和平台差异测试。
- [ ] `--help`、README、实现和测试同步更新。
- [ ] 候选包已从空目录安装并运行。
- [ ] 验收结论明确区分本地、平台、远端服务和公共发布层。
