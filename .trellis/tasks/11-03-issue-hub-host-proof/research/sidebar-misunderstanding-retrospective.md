# 缺陷复盘：将原生悬浮侧栏误解成多个主入口

## 1. 根因分类

- B：跨层契约。MCP global 入口声明与宿主原生悬浮导航的数据源不是同一机制。
- D：测试目标错误。旧断言要求两个仓库工具带 global，验证了实现者选定的结构，没有验证用户要求的单主图标及原生浮层。
- E：隐含假设。把“主导航里出现仓库名称”当成“插件悬浮栏里出现仓库子项”，并从部分宿主源码误推第三方可接入。

用户已明确给出内置首页、资料空间、定时任务和代码审查作为参照；本次语义和源码直接定位成因，因此不编造多个运行时猜测或概率排名。主图标数量另以确定性红绿回归验证。

## 2. 旧验证为何没有发现

需求澄清的选项只区分“原生侧栏”与“页面内导航”，未分开主图标列表和悬浮子导航。用户选择原生，没有同意生成多个图标。

SDK 全局入口可注册、多个工具可被发现，只证明入口层能力。原生浮层还需要宿主可调用的数据源、状态和点击目标契约，之前没有追到这一层。

21 项测试及安装校验当时均可通过，因为验收条件本身错误。用户观察到三个图标是实际反证，不能解释成用户尚未刷新或没有正确点检。

## 4. 系统性影响

入口注册、页面显示、原生子导航和完整业务流要分别验收。以后涉及“侧栏”“面板”“窗口”等过载词时，先明确触发位置、出现区域、渲染主体与对象数量，再选协议。

不能把第三方可调用性从内置功能的源码存在推导出来。仅能找到 fixed registry 或专用桥接时，应记录能力缺口，不能先实现近似效果并沿用“原生”称呼。
