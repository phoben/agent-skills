# Trellis 项目接入

在用户指定的项目中判断当前缺什么，给出可审核的方案，按授权接入并复检。可以单独为项目配置 Trellis，也可以承接 [issue-init](../issue-init/SKILL.md) 交来的 Trellis 缺项。

## 查清现状

核对目标仓库、工作区、启用的平台以及当前会话是否已绑定任务。查看项目实际的需求、评审、测试、验收和交付习惯。优先保留已运行的默认流程和任务绑定。先检查 Trellis CLI、项目目录、原生选择、角色、Hook 注册、技能及模型。内容由现有仓库决定，勿从技能目录或另一项目套用。

配置已存在时按可用的 trellis-meta 对照项目真实文件。发现流程及其适用范围时使用[流程设计与发现](references/workflow-design.md)。诊断阶段以只读检查为主。分别说明缺失、可复用、需要用户决定和待实跑项。

## 确定方案并接入

先用项目实际场景说明每条流程由谁处理、何时批准、每步交什么、通过什么条件才能往下走。空白项目先建立一条默认流程，确有不同的工作方式时再增加变体。有成熟流程时明确增量，说明活动任务和原有宿主是否会受影响。

计划应列出默认及变体、节点和工件、发现与选择规则、技能路由、各宿主角色和模型、拟改文件、拟用官方命令和验收用例。全局安装、项目初始化、切换默认、变更既有任务绑定以及远端动作分别写明，由用户批准适用范围。

按[安全接入与验收](references/setup-verification.md)应用。官方命令负责 Trellis 原生安装、初始化和更新，项目流程、路由及适配使用项目自建文件。处理已有仓库前查看差异，保留原生文件、现有规范、用户改动与其他宿主。

## 复检与交接

回传目标仓库、CLI 和宿主、默认及变体路径、候选能否选用、实际启用的角色和 Hook、已核验项及遗留阻塞。区分静态配置、原生流程读取、Hook 回放和真实新会话。动态新增或改名变体应能被发现，已有任务要按原绑定执行。

项目同时需要 Issue 管理时，将接入结果交回 [issue-init](../issue-init/SKILL.md) 配置 Issue 合同。具体 Issue 由 [issue-triage](../issue-triage/SKILL.md) 核对来源和任务，推荐可用流程并交给主会话。技能之间共用发现工具，无需反复初始化。当前技能停在项目接入与验收。
