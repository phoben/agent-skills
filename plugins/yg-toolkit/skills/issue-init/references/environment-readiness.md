# 环境补齐与完成标准

## 从哪里开始

目标项目可能只有代码，也可能已经有成熟流程。先核对用户指定目录、工作区、Git 与远端身份，不从技能安装目录推测目标。不要求用户先提供 Issue 编号或手写合同；缺少这些正是初始化要解决的事项。

先读实际 AGENTS、贡献规范、Issue 模板和流程资料。只做必要检查，不读取 `.env`、凭据文件或输出远端 URL 中的账号、密码与令牌。检测结果中的缺项不自动授权安装、登录、初始化仓库或写入 GitHub。

## 诊断命令与结果

```text
node <issue-triage技能目录>/scripts/issue-tools.mjs doctor --root <项目>
node <issue-triage技能目录>/scripts/issue-tools.mjs doctor --root <项目> --workflow existing
node <issue-triage技能目录>/scripts/issue-tools.mjs doctor --root <项目> --workflow trellis --platform codex
node <issue-triage技能目录>/scripts/issue-tools.mjs doctor --root <项目> --workflow trellis --platform claude --remote
```

`--workflow auto` 为默认值，仅用于发现和提示，不表示自动安装或选择 Trellis。`existing` 表示适配项目已有／经确认建立的流程，`trellis` 表示用户已选择的方案。`--platform` 指本次实际使用的平台；未指定时不能假定某个目录就是当前宿主。

当前工具内建 Codex、Claude 的项目 hook 注册检查。其他平台或自定义入口由主会话按实际配置核实并补证，不套用这两个平台的结果，也不要求用户更换平台。

默认不联网。`--remote` 使用已存在且已认证的 gh 做只读检查，不执行登录、创建标签或其他写入；主会话可用当前平台实际可用的连接器补查，gh 缺失不等于项目无法接入。使用企业 GitHub 时核对实际 host，不回落到 github.com 的其他仓库。

有效诊断输出 JSON，退出码为 0；存在缺项也属于有效报告，不代表就绪。错误参数或无法读取目标目录返回非零。主要字段：

| 字段 | 含义 |
|---|---|
| `schema_version`、`root` | 报告结构版本及明确的目标项目 |
| `workflow_mode`、`selected_workflow` | 本次检查模式与已识别的承载方式，不保存候选名称表 |
| `checks` | 分项结果，状态为 pass、missing、warn、unknown、not_applicable，包含必要性、依据和下一步 |
| `readiness.local` | 本地条件 ready、needs_setup 或 needs_verification；必需项未知不能算 ready，也不代表整体接入完成 |
| `readiness.github` | not_checked、readable、needs_setup 或 needs_verification；读取成功不等于对象和权限全部齐全 |
| `readiness.behavior` | not_verified；诊断不会冒充新会话行为验收 |
| `status`、`next_actions` | needs_setup 或 needs_verification，以及需继续执行的动作 |
| `read_only:true`、`complete:false` | 工具只检查，不写目标；整体完成由主会话结合额外证据判断 |

诊断不能看到的宿主连接器、用户级配置、共享账号 Type／字段和实际业务批准记录均需另核。不要通过额外输入“已完成”标志，让工具跳过验收。

## 缺项如何处理

| 检查结果 | 处理方式 |
|---|---|
| 只有代码，没有 Git 或远端 | 确认沿用已有仓库还是创建新仓库，以及归属和可见性；批准后处理，不擅自公开项目 |
| 没有 GitHub 访问方式 | 优先可用连接器；需要 CLI 时核对安装来源和登录方式，用户完成交互式登录后复检 |
| 没有 Issue 规划 | 调研真实工作习惯，提出 Type、阶段、阻塞、模块、完成条件和权限方案；不用通用模板代替必要问答 |
| 已有非 Trellis 流程 | 优先复用；Node、Python、Trellis 等只按实际需要检查，不为统一工具而强制迁移 |
| 没有任何流程 | 通过业务场景选择精简规则或 Trellis；明确谁澄清、谁批准、谁实施、如何验证及交付 |
| Trellis CLI 已有，项目尚未初始化 | 交给 [trellis-setup](../../trellis-setup/SKILL.md) 核对目标、宿主和批准范围 |
| `.trellis` 有目录但核心或 Agent 接入残缺 | 记录确切缺项，由 trellis-setup 预览和补齐平台接入 |
| hooks 文件存在但没有生效注册 | 检查本机实际配置及信任要求；目录存在不算启用，无法核实标为待验证 |
| 没有 Node，无法运行辅助工具 | 主会话使用已有只读能力核查；只有所选方案确实需要时才提议安装 |
| 远端缺标签／Type／字段或权限 | 展示具体拟补对象和影响，复用已有定义；共享范围单列，批准后创建或由管理员处理 |
| 连接失败或权限结果未知 | 记录最后成功步骤、缺项和恢复入口，不宣称就绪、不重复投递未知写入 |

## 补齐与授权顺序

用一个真实场景解释选择，例如“新会话收到客户反馈的 Issue，先核原文和已有工作，再推荐本次流程；批准规划后才创建任务”。没有项目流程时，说明精简规则和 Trellis 下谁负责下一步、工件放哪里、如何验收，给出基于项目事实的推荐。

集中列明所选方案的动作清单：必要依赖、登录、项目接入／修复、本地规则、远端对象和验收。用户已经批准具体范围时直接推进，不把同一安装或文件差异反复拆成确认。遇到范围实质变化、全局／共享影响或新的远端动作时说明差别，再取得对应授权。

选择 Trellis 后，将目标仓库、宿主、现有流程、缺项及已批准范围交给 trellis-setup。该技能负责核对官方命令、接入和验证。收到回执后，issue-init 核对可用默认、变体和是否有待验证项，再继续制定或落实 Issue 合同。

选择现有流程时，缺少的最小流程写到实际 AGENTS 非受管区或规范真源。说明来源如何关联工作项、如何识别正在处理的事项、阶段证据及继续入口，不伪造 Trellis Task／runtime。最后再用 plan-init／apply-init 接入合同和受管入口；辅助工具不会替代这部分流程设计。

安装、登录、本地接入和远端对象不是一个事务。部分完成后保留成功项，复读再补缺项；不为重试清空任务、覆盖配置或重建已有对象。

## 什么时候算完整

主会话按已选择方案逐项报告证据：

1. 项目与远端归属清楚，当前 Agent 有实际可用的访问方式。
2. 所需依赖及工作流接入有效。无 Trellis 方案不因未安装 Trellis 判失败；选择 Trellis 的方案不能在仅有目录时算通过。
3. 项目规则完整可执行，必要远端 Type／标签／字段已回读核实；未采用的对象记为不适用。
4. 新会话只提供真实 Issue 编号或链接，先完成前置处理，动态给出流程清单与推荐，不先泛化询问建任务、不自动实施。
5. 有另一活动事项时保持原指针和范围，独立工作建议隔离，真实子项按批准处理。
6. 重复初始化不产生无意义变化，手改内容和原生受保护文件保留。

正式项目尚无可读 Issue 时，列出首次行为验收待办。需要创建验证 Issue 必须在具体批准范围内；合成回放可验证本地流程，不能证明真实远端访问及标签配置。还缺人工登录、权限、对象或新会话验收时，只报告部分完成和继续入口。
