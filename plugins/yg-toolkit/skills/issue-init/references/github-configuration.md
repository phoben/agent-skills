# GitHub Issue 配置指引

Issue Type 用于共享分类，Issue Form 是仓库的提单入口，Label 补充分拣、模块或其他筛选信息。先确定项目实际需要的 Type，再为每张 Form 列出提交后预设的 Type 和自动添加的 Label，记录由分拣人员补填的项。同一个 Type 可以接收多张表单。需要团队维护的优先级等值，按项目现有做法在分拣阶段填写。

## 选择接入规模

用结构化提问让用户三选一。根据实际提单量、分工和筛选需要给出推荐，放在首位并标注“推荐”。下表是配置起点，按实际需要选择和复用对象。用目标项目的同一真实案例说明三档差别，没有案例时可用假设的“导出报表失败”。

| 规模 | Issue Form | Issue Type | Issue Label | 提单和处理示例 |
| --- | --- | --- | --- | --- |
| 初创规模 | 精简，每张 1–2 项。只为常用提单场景准备入口。 | 保留最常用的分类，例如缺陷和需求。 | 保留能驱动下一步的少量标签，例如待分拣。 | 提交人描述导出失败，表单自动关联缺陷和待分拣，分拣人员遇到信息不足再追问。 |
| 标准规模 | 标准，每张 2–4 项。为缺陷、需求等主要场景分别收集信息。 | 在基础分类上补充有独立管理用途的类型，例如内部任务。 | 按需增加模块和阻塞标签，方便分工和跟进。 | 提交人填写现象、复现步骤和影响范围，分拣人员按报表模块交给对应团队。 |
| 成熟规模 | 详细，每张 3–6 项。同一 Type 下可为反复出现且所需信息不同的场景分别设入口。 | 保持基础分类稳定，仅为有独立分工、生命周期或统计口径的事项扩展 Type。 | 按已有治理需要补充分组标签，例如模块、阻塞原因或交付范围。 | 提交人选择报表异常入口，再提供预期结果和发生环境。该单仍归缺陷，团队可按模块及阻塞情况跟踪。 |

按每张 Form 独立计数。表单正文里可填写或选择的字段都计入，包括选填项。GitHub 自带标题、静态说明、自动设置的 Type 和 Label，以及绑定到 Type 的原生 Issue Fields 不计入。有明确需要时可以为个别 Form 选用另一档，经用户确认后写入方案。只有缺失后会妨碍处理的字段才设为必填。

## 确认配置语言

规模选定后，向用户确认 Form、Type 和 Label 的配置语言。可根据明确的项目约定或当前对话语言提出推荐。默认三者采用同一项已确认的语言，用户有多语言约定时记录各对象适用的语言。语言规则覆盖 Form 入口名称、描述、字段文案和选项，以及 Type、Label 的名称和描述。项目合同沿用既有语义键，映射值填写实际名称。

## 集中确认旧配置的处置建议

新配置草案形成后，集中列出不符合已确认语言或用途规范的旧 Form、Type 和 Label，逐项说明旧名称、所在范围、原因、拟用名称或替代项，以及引用和影响。按对象检查历史 Issue、PR、模板、筛选视图、配置和自动化。共享 Type 还要核对其他仓库的使用情况。说明已知和未核实的范围。

用结构化提问让用户选择保留、改名或删除，允许不同对象采用不同处置。以保留作为未选对象的默认处理，说明改名或删除后需更新的链接、引用和已有记录。影响其他仓库或共享影响无法确认时，列明需所属管理员处理的事项。将用户选择、迁移和验收动作汇总进最终方案。获准实施后，仍有引用的旧对象按方案协调更新，删除前完成并验证所需迁移。
