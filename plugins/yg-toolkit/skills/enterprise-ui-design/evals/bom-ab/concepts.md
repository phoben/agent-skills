# 标准 BOM 维护：结构方向发散

## 共同判断

这个任务的难点不是把三条子件放进一张更漂亮的表，而是让用户在四个关键时刻始终知道自己正在处理的**成品、版本和整份清单**：先从多个成品及版本中定位对象；随后修改两类约束不同的字段；保存前确认整树；最后把“正在生效的 V3”复制为“保持原样的 V4 草稿”。

A 的基线采用“筛选栏 + 左侧成品清单 + 右侧版本页签与表格”。它紧凑、熟悉，编辑时也能同时看到全部三条子件。以下方向不以增加徽标、提示、卡片或装饰获得新鲜感，而是重新安排“对象选择、版本关系、编辑范围、核对时刻”在空间和时间上的主次。

所有方向都应保留：模拟数据边界；已有 SKU 的规格不可编辑；临时物料必须为虚拟件；未保存修改的离开保护；复制仅允许来自生效版本且明确说明 V3 不会被改变。它们描述的是可原型化的页面结构，并非真实服务能力。

---

## 方向一：版本谱系工作台

### 核心结构

把“版本”从当前表格上方的次级页签，提升为页面的主导航。页面上半部是一条横向版本谱系：成品标题居中，V2（历史）→ V3（生效）→ V4（草稿，如已复制）的节点连成时间线；下半部是当前节点的完整子件表。左侧只保留可搜索的成品索引，进入 `CP-1008` 后，用户首先进入版本谱系，再进入某一版本的内容。

谱系节点承担版本状态、复制入口和版本之间的关系；内容区只承担“这个版本的整份 BOM”。这样 V3 与 V4 在视觉上是有因果关系的业务对象，而不是两个相邻标签。

### 四个时刻的视线与动作

| 时刻 | 用户先看什么 | 用户怎么做 |
| --- | --- | --- |
| 定位 | 左侧成品索引中的 `CP-1008`，随后自然落到谱系里醒目的 V3 生效节点和其左侧 V2 | 搜索或点选成品；用谱系确认 V3 是当前生效、V2 是历史，再点 V3 打开清单 |
| 编辑 | V3 节点持续留在表格上方，视线再进入两处可编辑单元格；已有 SKU 的规格显示为不可进入的资料值 | 修改外壳用量、临时垫片规格；离开节点或切换版本时，由节点上的“有修改”状态触发保护 |
| 全量核对 | 视线从局部编辑回到标题明确的“V3 完整组成”表；表格以连续清单显示所有子件 | 用表头的来源、用量、规格、虚拟件列逐行扫描；保存动作附着在 V3 节点所对应的内容区底部 |
| 复制版本 | 视线先回到 V3 生效节点，再沿谱系右侧的“复制为新草稿”动作看到预期落点 V4 | 确认“由 V3 创建 V4 草稿，V3 保持生效”；完成后点亮新节点，打开 V4 后核对三条子件和修改值 |

### 风险与化解

- 版本很多时横向谱系会拥挤。只展现当前成品的近邻版本，较早历史归入“更多历史版本”，并保持 V3 与当前草稿可见。
- 用户可能把谱系理解成发布流。用“历史 / 生效 / 草稿”的事实状态表达，避免加入审批、发布等未实现动作。
- 子件极多时底部表格仍需滚动；版本身份应粘在表头，保存前用明确的“完整清单核对”阶段承接。

### 为什么不是换分栏或卡片

它改变了信息的第一层级：版本从成品详情的局部切换器变成用户选择和理解对象的主路径，并把“复制”从表格工具栏动作改为谱系上的新分支。

## 方向二：逐层展开的 BOM 档案夹

### 核心结构

页面像一份打开的制造档案，而非数据台账：第一层是成品封面（SKU、名称、当前版本）；第二层是版本目录（V3、V2）；第三层才展开某一版本的“子件清单页”。同一时刻只完整展开一个层级，前一层以窄条档案索引保留在顶部。进入编辑后，清单页扩展为整页，提交前回到一个只读的“待保存档案页”进行核对。

这是一种受控的纵向钻取：用户通过“打开档案”进入对象，通过“返回目录”离开对象，而不是在密集的左右区域间不断找焦点。

### 四个时刻的视线与动作

| 时刻 | 用户先看什么 | 用户怎么做 |
| --- | --- | --- |
| 定位 | 成品封面列表，视觉上突出 SKU 和名称；打开 `CP-1008` 后的版本目录中 V3 与 V2 垂直排列 | 搜索并打开成品；在版本目录选择 V3，借状态词而非表格列判断生效与历史 |
| 编辑 | 清单页顶端的档案路径 `CP-1008 / V3（生效）`，再看可改字段；字段旁直接呈现其资料来源规则 | 进入“编辑此版本”，在连续表内修改两项；尝试离开清单页时先决策保存、放弃或继续编辑 |
| 全量核对 | 从编辑态进入只读核对页，视线不再被输入框吸走，而是沿完整清单逐项阅读 | 选择“核对后保存”；核对页固定显示 3 个子件总数、临时物料和虚拟件条件，确认后保存 |
| 复制版本 | 回到 V3 档案头部的版本操作，操作后视觉结果是版本目录新增一页 V4 草稿 | 在明确对象提示中确认复制；进入 V4 档案页，确认内容继承，再可返回目录看 V3 仍生效 |

### 风险与化解

- 核对页看似额外一步，熟练用户会觉得慢。把它只放在“有修改且保存”路径，未修改浏览不用经过它。
- 上下文可能因钻取而丢失。每页固定显示简短路径和可返回的上级名称，不能仅用面包屑图标。
- 频繁跨 SKU 对照的用户效率不高，适合以单一 BOM 的准确维护为优先的场景。

### 为什么不是换分栏或卡片

它改变了任务节奏：定位、编辑、核对、复制是四个有明确入口和退出条件的页面状态，核对不再只是同一张可编辑表的最后几秒扫视。

## 方向三：变更单覆盖在基线之上

### 核心结构

V3 的完整 BOM 先以稳定的只读基线展示；点击编辑后，不把整张表变成输入表，而是进入“本次变更单”模式。页面主区仍是完整子件清单，只有被选中的外壳、缓冲垫片在右侧形成两条变更记录：`用量 2 → 2.5`、`规格 厚度 1.0mm → 厚度 1.2mm`。保存前，用户核对的是“基线完整清单 + 本次两项覆盖”的合成结果。保存后覆盖被写入 V3 的新基线。

版本区可以放在上方横条或左侧轻量索引，重点是编辑的认知对象从“表格单元格”变为“对完整 BOM 的两项变更”。

### 四个时刻的视线与动作

| 时刻 | 用户先看什么 | 用户怎么做 |
| --- | --- | --- |
| 定位 | `CP-1008` 的 V3 完整基线，V2 只作为版本索引中的历史参照 | 选成品和 V3；从一眼可读的三条基线确认来源、用量、规格 |
| 编辑 | 先点选需要变更的行；视线从表中被选行转到“本次变更”区，那里只出现可提交的两个差异 | 对外壳添加用量变更，对临时垫片添加规格变更；已有 SKU 规格根本不提供变更入口，临时件的虚拟属性在变更记录中锁定显示 |
| 全量核对 | 视线沿主表扫描完整三条，改动以“原值 → 新值”嵌在对应行；同时看右侧变更单确认只有两项 | 检查整表的合成值和变更数量，再保存；未保存状态表达为“有 2 项待提交变更”，而非模糊的小红点 |
| 复制版本 | 在 V3 的稳定基线状态执行复制，先看到“复制的是已保存 V3 的完整内容” | 保存后复制生成 V4；打开 V4 时没有未提交覆盖，直接看到继承后的三条基线及修改值 |

### 风险与化解

- 业务人员可能误解“覆盖”是长期差异层。文案必须明确它只是本次尚未保存的修改，保存后成为 V3 内容。
- 如果一次修改几十条，变更区会变成第二张表。可按物料分组、显示计数，主表仍作为全量事实来源。
- 增加了交互心智，需保证点行、撤销单项和恢复原值直接可见。

### 为什么不是换分栏或卡片

它把编辑模型从“直接改整份表”变成“维护一份基线上的可审视差异”。这直接改善保存前的全量核对，并使未保存离开保护有具体内容可说。

## 方向四：装配清单阅读带

### 核心结构

将子件主区设计成一条从上到下的“装配阅读带”：每个子件是一行连续的业务句，而非被竖线割开的表格单元格，例如“`02 外壳｜已有 SKU｜生产用｜2.5 件｜黑色（SKU 资料）｜必需`”。行内只把当前可改的数值或临时规格开放为编辑控件。左侧是一条窄的编号导航带，右侧不承担第二份信息，只在小屏时收起筛选。

版本通过阅读带上方的版本带呈现：当前 V3 占主位，V2 作为可回看的前序版本，复制结果 V4 作为后续草稿。这让视线按“成品 → 版本 → 子件 01 至 03”的固定阅读顺序移动。

### 四个时刻的视线与动作

| 时刻 | 用户先看什么 | 用户怎么做 |
| --- | --- | --- |
| 定位 | 顶部的成品检索结果和版本带，随后顺着 01、02、03 的阅读带看三条子件 | 选 `CP-1008` 与 V3；滚动或点编号导航定位子件，信息不会因横向列太多而断开 |
| 编辑 | 视线停在 02 的“2 件”和 03 的“厚度 1.0mm”，其余文本保持阅读状态 | 直接在句内替换数值和规格；已有 SKU 的规格表现为资料文字，临时件行固定展示“虚拟件”约束 |
| 全量核对 | 以编号导航上的完成状态和连续阅读带重新从 01 扫到末行 | 保存前从顶部进入“阅读核对”，把所有编辑控件收回为结果文本；用户按物料逐条确认完整范围 |
| 复制版本 | 版本带使视线从 V3 向后移动到“建立 V4 草稿”的占位节点 | 确认复制对象和结果；V4 出现后按相同 01 至 03 阅读顺序验证继承内容，V3 仍保留生效标记 |

### 风险与化解

- 对十几列、上百行的传统台账用户，句式会显得不够“可扫列”。保留紧凑的字段顺序、可切换的字段强调，不将每行拆成冗长描述。
- 大数量 BOM 的纵向长度会增加。编号导航应能显示异常或已修改行并提供跳转，但不取代连续全量阅读。
- 用户可能把“阅读核对”当成只读锁定，需在保存后明确返回编辑的入口。

### 为什么不是换分栏或卡片

它改变了子件信息的语法和扫读方向：从二维字段矩阵转成以一件物料为一个完整判断单位的线性装配叙事，特别适合同时识别来源、用量、规格与虚拟件约束。

## 方向五：双版本对照台

### 核心结构

页面始终保留一个“参照版本”和一个“工作版本”。对 `CP-1008`，左半部是 V2 历史或已保存 V3 的只读参照，右半部是 V3 工作内容；两边使用相同子件行顺序并以中央的物料编号轴对齐。默认在选择 V3 时，左侧自动带出 V2；编辑后，左侧可切为“V3 保存前”，右侧为“V3 当前修改”，形成一次修改前后的对照。复制完成后可把左侧设为 V3、右侧设为 V4。

这条路线面向“版本为什么不同”比“单表录入最快”更重要的制造维护场景。它令版本与复制的结果从文字承诺变成同屏可见的对应关系。

### 四个时刻的视线与动作

| 时刻 | 用户先看什么 | 用户怎么做 |
| --- | --- | --- |
| 定位 | 成品选择后先读双栏标题：左 V2 历史、右 V3 生效；中央编号轴确保看的是同一个子件 | 在版本选择器确定工作对象 V3；左右对照辨认 V2、V3 的版本身份，再聚焦右侧三条子件 |
| 编辑 | 右栏是唯一可编辑区，左栏始终是只读参照；视线可即时回看原值或历史值 | 修改右栏外壳用量和临时规格；已有 SKU 规格在右栏也只读，临时件的虚拟标记在两侧一致 |
| 全量核对 | 把左栏切到“保存前 V3”，逐行横向核对右栏“当前 V3”，差异只在两处 | 先确认只有预期两行不同，再纵向检查三条都存在；保存后左右栏重新一致，给出明确完成感 |
| 复制版本 | 左栏固定 V3 生效，右栏的目标标题预告 V4 草稿 | 确认复制；右栏切为 V4，用户同屏看到三条一一对应且修改值相同，左栏 V3 的生效状态不动 |

### 风险与化解

- 1280 宽度下双栏会压缩字段。使用中央对齐轴、冻结物料名称，次要字段可在行内展开；小视口允许临时切换为上下对照，但保持同一对照语义。
- 对本任务只有三条子件，结构可能显得重。原型需用清晰的“为何对照”动作证明价值，不能只是重复同一份数据。
- 左右列视觉相似，必须让工作栏始终有明确编辑边界，避免改错版本。

### 为什么不是换分栏或卡片

它不是把主从信息并排，而是让两个版本成为同一个工作单元，并以物料级对齐支持“修改前后”和“复制后继承”的实质性验证。

## 最值得原型化：方向三「变更单覆盖在基线之上」

推荐原因是它最直接对应本题最大的业务风险：保存会整树提交，用户却只修改两处。成熟后台的表格基线可以保留，用户仍能迅速定位、扫读来源和规格；但进入编辑后，未保存的内容被收束为可数、可撤销、可逐项确认的变更单。保存前的“全量 BOM 事实”与“本次意图”同时成立，避免为了核对而再造一层冗长流程。

它也能把复制动作做得更可信：只有变更单清零、V3 成为稳定基线后，才能复制到 V4；复制后的 V4 没有悬而未决的编辑覆盖，用户看到的就是继承完成的三条子件。原型重点应检验三个可观察结果：用户是否知道自己只改了哪两项；是否能在不离开完整清单的情况下确认三条子件；是否能分清“保存 V3”和“复制出 V4”是两个连续但不同的结果。
