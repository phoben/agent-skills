# 活字格插件测试

先明确本次交付的是测试方案、可运行的用例，还是候选包验收结果。规划任务给出场景、执行入口和通过条件；实现任务从实际插件入口编写并运行用例；验收任务记录本次构建和宿主上的观察结果。

## 确定测试范围

查看插件清单、项目引用、实际参与构建的入口、已有测试和发布目标。逐项写清插件类型、最低宿主版本、承诺支持的版本及运行位置。一个包包含多种扩展时分别列出。区分设计器、发布服务器和浏览器；命令还要区分页面调用、计划任务等实际支持的场景。项目提供版本文档工具时，用它核对涉及的宿主接口，并对照目标 SDK。

## 选择用例和工具

| 验证对象 | 默认做法 | 通过依据 |
| --- | --- | --- |
| 业务逻辑 | C# 用 xUnit，JS/TS 用 Vitest。已有同类框架时沿用，选择与目标运行时兼容的版本 | 对正常、边界和失败输入断言业务结果 |
| 插件入口与外部服务 | 调用实际公开入口，只替换用到的宿主接口、时钟或外部服务；需要检查 HTTP 请求管道时用 ASP.NET Core TestServer | 核对输入、返回值、持久化或外部请求，以及失败后发生的操作次数 |
| 最终 ZIP | 由脚本解包，检查插件标识、版本、入口程序集、资源及依赖 | 用独立维护的支持范围核对最低宿主版本和实际编译引用；检查清单声明的文件确实在包内 |
| 真实活字格 | 维护最小验收应用。设计器验证导入、配置、保存重开；发布后的页面用 Playwright，服务端按相应入口触发 | 核对用户可见的结果、数据和日志。升级测试用旧版插件实际保存的应用副本 |

按本次插件类型选场景：

- **服务端命令**：测试公式求值后的空值和类型、输出参数、空结果和异常。涉及写入时，分别验证提交前失败和提交后结果未知，核对副作用次数。声明支持后台运行时，在无页面上下文中触发一次。
- **页面命令**：把命令放进真实命令链，由下一条命令读取其结果。覆盖异步成功和失败，检查后续命令是否按约定执行，重复点击是否产生多余操作。
- **单元格类型**：同页放两个独立绑定的实例，测试宿主回填、用户编辑、只读、联动和保存回读。离开再进入页面，检查事件是否重复触发。
- **中间件**：在测试管道中验证路径、方法、身份和异常响应，用下游计数验证普通请求恰好放行一次。在已发布的活字格应用上同时访问目标接口与普通页面，确认实际注册顺序和权限效果。

## 编写与维护用例

用业务结果命名，每条用例写明前置条件、触发动作、可观察结果。缺陷回归、人工用例和跨版本用例保留稳定编号、适用版本及执行入口。例如「CELL-EDIT-003 修改经办人并保存后，复核人仍为原值」：给两个字段预置不同值，改第一个字段，保存重开后分别核对。前端测试覆盖实例隔离，真实页面验证保存回读。

在成本最低且能观察到故障的层次保留回归。修复缺陷时尽量验证旧实现失败、修复后通过。自动化脚本与产品改动一同评审；手工清单记录必须经过设计器或特定环境的步骤。测试数据可重建、可清理、可并行隔离；外部服务默认用本地替身，真实联调用专用测试数据。浏览器按可见名称或稳定标识定位，等待业务结果出现，失败时留存脱敏轨迹。保留首次失败证据并定位偶发故障。

## 构建与发布

1. 开发机提供一条可重复执行的快速测试命令。合并前在干净环境使用目标 SDK 编译并执行适用的测试，报告通过、失败、跳过及发现数量。必测用例缺失或意外跳过时检查发现配置。
2. 从候选构建取 ZIP，执行包检查，记录提交、包版本及 SHA-256。为声明支持的宿主版本安排验收，覆盖最低版本、新装和从已有发布版升级；首次发布记录升级项不适用。
3. 每种交付的插件类型选一条关键业务流程，在匹配的真实宿主执行。设计器缺少可验证的自动化入口时，保留简短人工步骤。真实宿主缺席时将该项记为待验收，写明缺少的环境。
4. 分别报告编译、核包、设计器、旧应用升级、目标运行端和业务结果。每项写明环境、执行入口、预期与实际结果、证据位置。正式发布沿用已验收的同一份 ZIP。
