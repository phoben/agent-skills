# Harness 分流

先完整读取 `.trellis/spec/config/framework-upstream-sync-guidelines.md`；它是长期分类合同，本文件只规定本次同步如何执行。

## 1. 建立 Harness 清单

列出候选提交中所有平台说明、Skills、Commands、Hooks、Agents、设置、工作流和 Trellis 文件。按职责和可观察行为分类，不能只看扩展名、目录或上游自称。

## 2. 四类处理

### 工具型能力

工具型内容提供可独立执行的操作能力，例如生成、迁移、诊断或验证。只有同时满足以下条件才建议引入：

- 本项目确实缺少该能力，且不是现有 Skill、脚本或 Trellis 工作流的重复包装。
- 依赖、路径、命令和平台在当前仓库可用。
- 内容不夹带与本项目冲突的规范型强制规则；混合内容应拆分，只保留工具能力。
- 有明确的可运行验证和维护归属。

选择项目实际支持的 Skill 目录；共享能力优先放在 `.agents/skills/`，平台专有入口保持薄层，避免复制两套长文档。

### 规范型内容

编码约定、目录约束、工作流规则、架构原则、审查清单和“必须/禁止”类开发要求属于规范型内容：

1. 提炼具体增量，不复制上游 Skill。
2. 在当前代码、配置或测试中验证前提；与本项目事实冲突的规则拒绝或改写为本项目真实边界。
3. 找到已有 `.trellis/spec/<layer>/index.md` 和最接近的 guideline，避免重复专题。
4. 取得通用规范写入授权后使用 `trellis-update-spec`，写入触发条件、正确边界和验证点。
5. 在同步记录中保存来源提交、已提炼规则、落点和拒绝原因。

### Trellis/Harness 基础设施

Hooks、Agents、Commands、设置、`AGENTS.md`、`CLAUDE.md` 和 `.trellis/**` 先与本地实现比较。上游删除也不能自动删除本地 Harness。

对上游 `.agents/**` 中的 Hook、Agent、Command，以及任何位置的 `AGENTS.md`，必须先形成逐项决策报告，至少包含：

- 来源提交、路径和上游想解决的问题。
- 当前项目对应的 Harness/Trellis 能力和差异。
- 可吸纳价值、重复能力、兼容风险与建议落点。
- 建议动作及理由：通常为**吸纳到项目 Harness**或**忽略**；若两者都不合适，明确需要用户另定方案的原因。

报告完成后等待用户决定；可以让用户对报告中已列明的多个项目作批量决定，但选择整个提交、批次或“全部建议合并”不视为这些 Harness 项的决定。用户未决定时保持待决，不写入文件，也不允许同步基线越过包含该项的提交。

- 用户选择**吸纳**：把有价值的行为融入现有项目 Harness，按本地 Trellis、Hook、Agent、Command 或 `AGENTS.md` 的真实职责做最小适配；不能直接复制、覆盖同路径文件或重建上游强制评估体系。
- 用户选择**忽略**：不改本地 Harness，并在同步记录中保存来源和忽略理由。
- 用户指定其他方案：按该方案重新评估影响与授权边界，明确后再执行。

其他 Trellis/Harness 基础设施同样先评估本地等价能力；确有增量时，设计成适合本地平台的最小改动并单独取得授权。

### 框架同步能力

任何负责发现、分析、合并或记录原作者框架更新的 Skill、Command、Hook 或 Agent 都与 `project-upstream-sync` 冲突。无论路径、名称或措辞是否包含 `framework-sync`，一律跳过并记录：

- 来源提交和路径。
- 判定其承担框架同步职责的证据。
- 跳过原因：保护项目级同步入口，避免上游覆盖本地 Harness 规则。

不得通过重命名、复制片段或创建兼容别名引入此类能力。

完成标准：每个 Harness 文件都落入且只落入一个主类别，混合内容已拆分；`.agents` 中的 Hook/Agent/Command 和 `AGENTS.md` 均已有用户决定或保持待决，框架同步类能力全部被阻断。
