# 内容融合

只有用户明确选定提交或变更组及待决策略后，才执行写入。

## 三方理解

对每个目标文件分别理解：

- **base**：本项目上次同步基线中的框架版本。
- **ours**：当前项目版本及基线后的本地定制。
- **theirs**：候选上游提交带来的增量。

把 `theirs - base` 的有效意图最小化应用到 `ours`。同一路径、上游新增或上游删除都不是直接覆盖/删除的充分证据。

## 融合规则

- 使用局部补丁修改已存在文件；新增文件也要先确认项目确实需要并适配其依赖和标识符。
- 保留项目名称、包名、数据库/Redis 前缀、端口、环境变量、业务行为和 Harness 定制。
- 标识符替换先预览，按完整标题或长字符串、连字符形式、下划线形式的顺序处理；数字端口只在已确认的配置位置替换。
- 配置只引入适用的新键或语义变化；依赖升级检查统一版本和兼容矩阵；SQL/迁移遵守本项目数据库与 Flyway 规范。
- 删除只有在确认本项目无引用、用户已授权且有可恢复依据时执行；上游删除不自动传播。
- 每次处理一个逻辑提交或可独立验证的变更组，并保留来源提交记录。

遇到无法判断的安全语义、数据迁移、生产配置、依赖破坏性变化或并发脏文件时停止该项，报告业务影响和可选策略。

完成标准：每处写入都能对应到已批准的上游意图，本项目无关定制保持不变，且该变更组具备可执行验证。
